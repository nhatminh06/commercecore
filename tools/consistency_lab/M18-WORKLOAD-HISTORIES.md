# M18: seeded concurrent workloads and observed histories

The test-only [M18Workload](../../src/test/java/com/commercecore/consistencylab/M18Workload.java) invokes existing Spring services against the disposable PostgreSQL container used by integration tests. It has no production endpoint or business-code change. The supported scenarios are `inventory_reserve` (competing standalone reservations on one SKU) and `checkout_retry` (concurrent calls and per-actor retries with one cart and one idempotency key). [M18WorkloadTest](../../src/test/java/com/commercecore/consistencylab/M18WorkloadTest.java) sets up the product and cart, executes both scenarios, and writes example histories to `build/consistency-lab/m18/`.

```sh
JAVA_HOME=/path/to/jdk-21 TESTCONTAINERS_RYUK_DISABLED=true \
TESTCONTAINERS_CHECKS_DISABLE=true ./gradlew :test \
  --tests com.commercecore.consistencylab.M18WorkloadTest --rerun-tasks
```

## Version 1 plan and history

`plan.schemaVersion` and `history.schemaVersion` are both `1`. A plan records `scenarioId`, UUID `runId`, integer `seed`, `initialStock`, `actorCount` (2–8), `operationsPerActor` (1–4), `timeoutMillis` (100–60,000), `startConstraint`, and up to 32 `operations`. Each operation has a stable `operationId` (`scenario/actor-N/step-N`), `actorId`, `step`, `type`, `logicalRequestId`, and `quantity`. For checkout, all calls share logical identity `shared-checkout-key`; the actual test-only key is derived from the run UUID and is not emitted. The seed deterministically permutes the plan's actor listing; it does **not** reproduce the runtime winner, thread schedule, network timing, or PostgreSQL lock order. Per-actor steps execute sequentially. A start latch releases actors only after all report ready.

The history stores the plan plus `provenance`, `clockSource`, `startedAt`, `finishedAt`, `quiescent`, `complete`, `quiescenceEvidence`, and `plannedCount` / `invokedCount` / `completedCount`. There is one observation per planned operation, ordered like the plan. Its `state` is `NOT_INVOKED`, `UNRESOLVED`, or `COMPLETED`. A completed call has outcome `SUCCESS` with a returned reservation/order ID, `REJECTED` with the business code, or `EXCEPTION` with an exception class. Invocation is written immediately before calling the service. The event offsets `invokedNanos` and `completedNanos` come from `System.nanoTime` in one JVM; wall timestamps are context only. A timeout triggers interruption and bounded pool termination. If the service call has no observed result, its observation remains `UNRESOLVED`; later per-actor operations remain `NOT_INVOKED`. `quiescent=true` means all actor tasks terminated before the history was frozen, **not** that every planned call completed. `complete=true` requires both quiescence and a completed observation for every planned operation. If termination is unconfirmed, the history says so and cannot establish a quiescent database boundary.

The writer and parser validate version, seed-derived plan, unique operation identity, observation identity, event shape, and count consistency. Serializing one frozen history twice gives identical bytes. Two runs with the same seed reproduce input plans when the same run ID is supplied, while their observations may differ. Histories contain no connection string, password, raw idempotency key, customer data, or payment credential. Generated files under `build/` are ephemeral test artifacts, not oracle verdicts.

## Evidence boundary and remaining work

The two current scenarios use CommerceCore PostgreSQL only. Checkout's transaction and advisory lock and reservation's conditional stock update are still the application mechanisms under test; the recorder merely observes calls. Payment initiation is excluded from this M18 plan because its external provider boundary and ambiguous outcomes require separately justified operation correlation. No M16 bundle is attached by this test: the shared integration-test database has no provisioned least-privilege M16 reader, and a run ID alone cannot isolate its rows. M16's independently qualified recorders and oracle remain unchanged. No Kafka history is reconstructed. An M19 checker would need a complete operation history, declared initial state and scope, and authoritative final state before testing a selected sequential specification. This M18 history alone does not prove inventory conservation, checkout linearizability, exactly-once effects, cross-store correctness, or global atomicity.

Hosted CI runs Gradle `test`, which includes this class if its Docker-backed backend job runs; it does not invoke opt-in `m17Test` or the six opt-in M16 PostgreSQL recorder tests. The M18 test uses the existing shared Testcontainers PostgreSQL instance, with unique per-run SKU and cart identities. Testcontainers reaps the disposable database at JVM exit. If an interrupted application call ignores interruption, `quiescent=false` is recorded after the two-second cleanup bound; the JVM may still need external test-process termination.
