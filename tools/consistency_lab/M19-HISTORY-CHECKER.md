# M19: independent bounded history checker

[`history_checker.py`](history_checker.py) reads the M18 version 1 JSON history **offline**. It imports no CommerceCore Java code, contacts no database or provider, and does not alter the input. It accepts only the two M18 scenarios, at most 8 actors and 32 operations, with strict plan, identity, event, outcome, interval, completeness, and provenance shape checks. Malformed evidence exits 2 with a diagnostic; it is not a business `FAIL`.

```sh
PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s tools/consistency_lab -p 'test_*.py'
python3 tools/consistency_lab/history_checker.py build/consistency-lab/m18/inventory_reserve.json
python3 tools/consistency_lab/history_checker.py build/consistency-lab/m18/inventory_reserve.json --exclusive-scope
python3 tools/consistency_lab/history_checker.py build/consistency-lab/m18/checkout_retry.json --exclusive-scope
```

`--exclusive-scope` is an **external test-scope attestation**, not a fact derived from the JSON. Use it only when the test set up the declared initial stock, the target SKU/cart/key had no unrecorded writers during the measured interval, and all calls used the recorded logical identities. Without that declaration the result is `INCONCLUSIVE`. M18's isolated tests create a unique SKU, and checkout creates a unique cart and key, before releasing actors; no other test code writes those identities during the bounded run. The JSON does not include the raw checkout key or a DB-backed proof of scope. A forged or incorrect attestation can make a false scoped PASS. No M16 snapshot is silently attached, and matching run IDs do not make databases atomic.

## Sequential specifications

**Inventory reservation:** Start with `initialStock`. Each successful `reserve(sku, 1)` consumes one available unit and returns a distinct reservation UUID. `insufficient_stock` is legal only when fewer than one unit remains. Stock never becomes negative. Release, confirmation, expiry, and unrelated writers are outside this model. The model comes from `ReservationService.reserve` and its conditional inventory update, but is implemented independently in Python.

**Checkout retry:** The M18 scenario has one existing nonempty cart with one item of quantity one and one shared checkout key. On the first successful call, one unit is consumed and a fresh order UUID is bound to that key. Every later call with that same key returns the same order UUID without consuming again. If stock is zero before the first success, `insufficient_stock` may be returned; it does not bind the key, so a later attempt is still eligible. The model follows the documented external contract of `CheckoutService.checkoutIdempotently`, not its transaction implementation. Other checkout rejection codes and exceptions are `INCONCLUSIVE` because this scenario does not record enough cart/catalog state to model them. A PASS checks returned identities and outcomes only: it does **not** prove only one order row, reservation, outbox event, or mapping was persisted.

For both models, an operation completed before another was invoked must appear first. Earlier steps of one actor must also precede later steps. Overlapping calls may appear in either order. Only `System.nanoTime` values from the one M18 JVM establish these constraints; wall timestamps are retained for context and never compared to another process. The checker explores eligible operations in stable plan order, memoizes model states, and returns one witness when all observations fit. If exhaustive search has no witness, `FAIL` reports a contradiction within the declared model. If a call is unresolved or not invoked, actors are not quiescent, scope is unestablished, an outcome is outside the model, or a limit is hit, the result is `INCONCLUSIVE`. Search is limited to 100,000 explored states and 2,000 ms by default; configurable bounds cap at one million states and 60 seconds. A 256 KiB input limit prevents unbounded CLI ingestion. For a fixed history and adequate budget, witness selection and verdict are deterministic; a run near the time cutoff can differ between PASS/FAIL and INCONCLUSIVE, never between PASS and FAIL.

Example: with stock 1, two overlapping reservations where actor 1 succeeds and actor 0 reports `insufficient_stock` have a witness `[actor-1, actor-0]`, even if actor 0 invoked first. Two successful reservations from stock 1 have no witness and return `FAIL`. A forced rejection that completed before any successful reservation with stock 1 also returns `FAIL`; overlap alone would not make that rejection impossible.

## Local qualification and limits

On 2026-11-24, seven checker mutation tests passed, including legal overlaps, oversell, impossible rejection, conflicting checkout IDs, malformed/incomplete events, unaccounted writers, and search-budget exhaustion. The M18 PostgreSQL suite regenerated histories without modifying their bytes afterward. With the explicit unique-identity/exclusive-scope test declaration, the four-operation inventory history returned `PASS` with witness `actor-1/step-0, actor-0/step-0, actor-0/step-1, actor-1/step-1`; the six-operation checkout history returned `PASS` with one order identity. The same inventory history without `--exclusive-scope` returned `INCONCLUSIVE`. These are observed-run, conditional sequential explanations, not proofs of all schedules or global linearizability.

M19 does not check payment ambiguity, Kafka delivery, cross-store state, transaction atomicity, or historical inventory restoration. The source history is a test-JVM observation with no cryptographic authentication. An operation completed after the bounded history freeze or an unobserved outside writer would invalidate a strong claim. M20 may package replay inputs and compare later runs, but a seed alone cannot reproduce scheduling.
