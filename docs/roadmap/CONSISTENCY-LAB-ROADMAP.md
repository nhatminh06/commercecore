# CommerceCore Consistency Lab roadmap

**M15a, M15b, and the scoped M16 database evidence milestone** are implemented. M16 is **PASS for bounded, authoritative database snapshots only**. The original M16 proposal in `CLAUDE.md` also called for Kafka/receipt capture and scenario-level invocation/result correlation. Those requirements have not been verified or silently removed: this scope decision explicitly defers them to later milestones, where delivery and operation histories can support their own claims. **M17 is locally qualified for isolated gRPC network faults. M18 is locally qualified for bounded CommerceCore inventory and checkout histories.** M19 onward is **PLANNED**. This test-only lab remains outside production request paths.

| Milestone | Scope and deliverable | Required evidence and acceptance | Risks, limits, non-goals |
|---|---|---|---|
| M15a IMPLEMENTED | Versioned synthetic evidence contract, offline oracle, fixture, mutation tests. | Positive, violated, incomplete, malformed, deterministic tests for every supported snapshot property; no unsupported PASS. | Synthetic data does not prove the running system. No collector, history, or real-run verdict. |
| M15b IMPLEMENTED | Qualify repo-native oracle; offline CI; current and future architecture diagrams. | Independent review of assumptions, mutation tests in CI, source-backed diagram review. | CI tests the checker only; GitHub-hosted execution remains unverified until a workflow run completes. |
| M16 PASS — DATABASE SNAPSHOT SCOPE | Read-only, bounded capture of four CommerceCore tables and the separate provider `provider_payments` table; each store has its own PostgreSQL snapshot and v2 provenance. | Isolated local PostgreSQL capture for both stores; distinct SELECT-only roles and denied writes; same-transaction schema, count and bounded ordered rows; explicit completeness; offline v1/v2 validation; positive, partial, drift, permission, and concurrent-write tests. Hosted CI runs the offline subset; Docker integration is opt-in locally. | Provider observation does not establish cross-store correctness. CommerceCore evidence omits `payments`; `run_id` labels captures but does not correlate an operation or create a shared boundary. The original Kafka/receipt and scenario-correlation goals are deferred, not qualified. |
| M17 PASS — ISOLATED NETWORK SCOPE | Opt-in test-only Toxiproxy between CommerceCore's real gRPC client and the real provider gRPC implementation backed by separate PostgreSQL. | Local run: five scenario tests plus no-toxic delay control; proxy traversal, `UNAVAILABLE` and `DEADLINE_EXCEEDED`, in-flight downstream cut after observed provider commit, recovery by lookup, idempotent repeat, negative injection and cleanup checks. M16 DB bundles remain independently qualified. See [M17 network faults](../../tools/consistency_lab/M17-NETWORK-FAULTS.md). | Both services run in one test JVM, with real TCP between them. Toxic API acknowledgment does not prove packet timing. No global snapshot, delivery history, production proxy, or public control API. Hosted CI skips opt-in network tests. |
| M18 PASS — BOUNDED COMMERCECORE SCOPE | Versioned seeded plans and observed histories for competing reservations and concurrent idempotent checkout retries in disposable PostgreSQL; strict actor/operation limits and timeout cleanup. | Local isolated integration tests observe successful/rejected calls, returned IDs, unresolved/not-invoked calls, deterministic serialization, malformed history rejection, and same-seed plan reproduction. | M19 PLANNED | Independent history checker for selected state-machine and concurrency properties. | Complete histories, mutation counterexamples, explicit assumptions and uncertainty. | No global linearizability claim from snapshots or wall clocks. |
| M20 PLANNED | Replay bundles and counterexample reduction. | One reproduced and reduced injected failure, with reproduction status and retained provenance. | Some races cannot be replayed exactly. No claim of deterministic scheduling. |
| M21 PLANNED | Offline execution-history debugger. | Every displayed assertion links to bounded captured evidence; observed and inferred ordering visually distinct. | Visualization cannot strengthen evidence. No live production dashboard. |
| M22 PLANNED | Integrated qualification and portfolio evidence. | Repeatable isolated scenario matrix, CI evidence, documented limits, independent reproduction. | Local experiments do not establish production availability or exhaustive correctness. No deployment automation. |
| M23 OPTIONAL, PLANNED | TLA+ model of selected domain transitions. | Explicit model assumptions, bounded counterexamples, model-to-code correspondence. | Model checking does not verify Java implementation. No whole-system formal proof. |

**Scope change record:** The original M16 wording in `CLAUDE.md` included bounded Kafka/receipt capture and correlation of test invocations/results. The accepted M16 deliverable here is independently qualified database evidence only. Kafka delivery-history reconstruction and end-to-end operation correlation require later collection and qualification; replay belongs to M20, and history/linearizability analysis belongs to M19 where adequate histories exist. Their absence does not become a database-snapshot PASS, and no cross-store or historical property is claimed by this M16 verdict.
